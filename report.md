## 1. Что реализовано

| Требование задания | Как выполнено |
|---|---|
| Сущности в ООП-паттернах, минимум 3 типа | Иерархия из 4 классов: базовый `Booking`, read-only `PastBooking`, редактируемые `SingleBooking` и `RecurringBooking` |
| Интерфейс `Editable` | Интерфейс с методом `validate()` |
| «Изменить» только для `Editable` | `instanceof Editable` в `MainFrame.updateEditButton()` |
| «Добавить» создаёт только редактируемые типы | Диалог предлагает только «Обычная» / «Регулярная» |
| Read-only типы только из файла | `PastBooking` создаётся только в `CsvLoader` |
| Загрузка из CSV, битые строки пропускаются | `CsvLoader` |
| Сохранение в CSV | `CsvSaver` |
| GUI: таблица, загрузить, сохранить, добавить, изменить, диалоги ошибок | `MainFrame`, `BookingTableModel`, `BookingDialog`, `JOptionPane` |

Уровень сдачи: **средний** (минимум + работа с корректным CSV). Собственные классы исключений с кодами ошибок (уровень «максимум») не делались — вместо них загрузчик собирает текстовые причины пропуска строк.

## 3. Модель данных

### 3.1. Диаграмма наследования

```
                  «interface»
                   Editable
                  + validate(): List<String>
                       ▲
                       │ implements
                       │
                ┌──────┴────────────────────────┐
                │                               │
   Booking (abstract) ◄── extends ── PastBooking (final, read-only)
      ▲   ▲
      │   └──────────── SingleBooking ─────── implements Editable
      └──────────────── RecurringBooking ──── implements Editable
```

`Booking` — общий родитель. `PastBooking` не реализует `Editable`; `SingleBooking` и `RecurringBooking` реализуют.

### 3.2. `Editable` — интерфейс

```java
public interface Editable {
    List<String> validate();   // пустой список = данные корректны
}
```

**Почему не маркерный, а с методом.** Проверка корректности нужна в трёх местах: в диалоге (перед сохранением), при загрузке из CSV (чтобы отсеять битые строки) и логически принадлежит самой сущности. Если сделать интерфейс с методом `validate()`, каждый редактируемый тип сам отвечает за правила своих полей (у регулярной брони — «выбран хотя бы один день», у обычной — проверка комментария), а GUI и загрузчик вызывают один и тот же метод, не зная конкретного типа. Маркерный интерфейс дал бы только флаг «можно менять», а валидацию пришлось бы размазывать по GUI. Это решение обосновывается в отчёте так: интерфейс — контракт «сущность можно менять и она умеет себя проверять».

### 3.3. `Booking` — базовый абстрактный класс

Общая часть всех броней («основная сущность» из задания).

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `int` (final) | Идентификатор брони, после создания не меняется |
| `room` | `String` | Название переговорной |
| `employee` | `String` | Сотрудник, забронировавший комнату |
| `start` | `LocalDateTime` | Начало брони |
| `end` | `LocalDateTime` | Конец брони |

| Метод | Назначение |
|---|---|
| геттеры / сеттеры | Доступ к полям (для `id` только геттер) |
| `csvType()` | Код типа для файла: `SINGLE`, `RECURRING`, `PAST` |
| `typeTitle()` | Название типа для таблицы |
| `extraCsv()` / `extraText()` | Значение дополнительного поля для файла / для таблицы |
| `overlaps(Booking other)` | Пересечение по времени в той же комнате — основа «проверки конфликта комнаты» из вариантов доп. операций |
| `validateCommon()` | Проверка общих полей: комната и сотрудник не пусты, нет символа `;`, конец позже начала |

Класс `abstract`, потому что «просто бронь» без вида в программе не нужна: `csvType()`, `typeTitle()`, `extraCsv()`, `extraText()` каждый наследник реализует по-своему (полиморфизм). Это позволяет таблице и сохранению в CSV работать с любым типом одинаково.

### 3.4. `PastBooking` — read-only тип

* `final`-класс, наследует `Booking`, **не реализует `Editable`**.
* Все сеттеры переопределены и бросают `UnsupportedOperationException` — второй уровень защиты: даже если в коде забудут проверку, изменить запись не получится.
* Новых полей нет. `id` и так неизменяем.
* Создаётся **только** в `CsvLoader` (строка с типом `PAST`). В диалоге добавления такого типа нет.
* В GUI при выборе такой строки кнопка «Изменить» заблокирована.

### 3.5. `SingleBooking` — обычная редактируемая бронь

* `extends Booking implements Editable`.
* Новое поле: `comment` (String) — комментарий/тема встречи.
* `validate()` = `validateCommon()` + проверка, что в комментарии нет `;` и переводов строк.
* В CSV дополнительное поле — сам комментарий.

### 3.6. `RecurringBooking` — регулярная бронь

* `extends Booking implements Editable`.
* Новое поле: `Set<DayOfWeek> days` (реализация `EnumSet`) — дни недели повторения. `EnumSet` выбран, потому что это компактный и упорядоченный по дням набор без дубликатов.
* `getDays()` возвращает неизменяемое представление — внутренний набор снаружи не испортить.
* `validate()` = `validateCommon()` + «выбран хотя бы один день недели».
* В CSV дни пишутся через запятую английскими названиями: `MONDAY,WEDNESDAY`. В таблице показываются по-русски: «пн, ср».
* Начало и конец брони задают время и первую дату, далее бронь повторяется по выбранным дням.

### 3.7. Наследование и интерфейс — в чём разница

* **Наследование (`extends`)** — переиспользование кода и **полей** одного родителя. `Booking` даёт всем броням общие `id`, `room`, `employee`, `start`, `end`. Класс может иметь только одного родителя.
* **Интерфейс (`implements`)** — только **контракт** без состояния: «умеет делать X». Класс может реализовать несколько интерфейсов.
* `Editable` — именно контракт, а не родитель: «редактируемость» — это свойство, не связанное с тем, чем является бронь. Поэтому `PastBooking` и `SingleBooking` имеют общего родителя, но различаются наличием контракта `Editable`.

## 4. Работа с CSV

### 4.1. Формат файла

Разделитель `;`, кодировка UTF-8, первая строка — заголовок. Даты в формате ISO-8601.

```
type;id;room;employee;start;end;extra
PAST;1;Альфа;Иванов И.;2025-03-03T09:00;2025-03-03T10:30;
SINGLE;3;Альфа;Сидоров П.;2026-10-05T10:00;2026-10-05T11:30;Обсуждение бюджета
RECURRING;5;Бета;Иванов И.;2026-10-05T09:00;2026-10-05T09:30;MONDAY,WEDNESDAY,FRIDAY
```

Все типы записаны в одном формате из 7 колонок; смысл `extra` зависит от `type`: пусто для `PAST`, комментарий для `SINGLE`, список дней для `RECURRING`.

### 4.2. `CsvLoader` — алгоритм

1. Открыть файл через `Files.newBufferedReader`, пропустить заголовок.
2. Читать построчно (`readLine`), пустые строки пропускать.
3. Для каждой строки `parse(line)`:
   * `split(";", -1)` — с `-1`, чтобы пустое последнее поле не терялось;
   * число полей должно быть ровно 7;
   * `Integer.parseInt` для id, `LocalDateTime.parse` для дат;
   * `switch` по `type` создаёт нужный класс (`default` — ошибка «неизвестный тип»).
4. Разобранный объект проверяется: `Editable` → `validate()`, иначе `validateCommon()`.
5. Проверка на повторяющийся `id` (`HashSet`).
6. Любая проблема бросает исключение, которое ловится в цикле: строка **пропускается**, а причина добавляется в список `errors` («Строка 5: конец брони должен быть позже начала»). Остальные строки продолжают загружаться.
7. Результат возвращается в `record LoadResult(List<Booking> bookings, List<String> errors)`.

Какие строки считаются битыми: неверное число полей; нечисловой id; неверный формат даты; неизвестный тип; неизвестный день недели; не проходит `validate()` (пустая комната, конец раньше начала и т. д.); повторяющийся id.

Ошибки уровня файла (нет файла, нет доступа, неверная кодировка) — `IOException`: пробрасывается в GUI и показывается диалогом ошибки.

### 4.3. `CsvSaver`

Записывает заголовок и по строке на каждую бронь. Благодаря полиморфизму (`csvType()`, `extraCsv()`) не нужно знать конкретный класс. Формат совпадает с форматом загрузки, поэтому сохранённый файл можно загрузить обратно.

## 5. GUI

### 5.1. `MainFrame` — главное окно

* Сверху четыре кнопки: «Загрузить из CSV», «Сохранить в CSV», «Добавить», «Изменить». По центру `JTable` с прокруткой.
* **Блокировка «Изменить»**: слушатель выбора строки вызывает `updateEditButton()`. Кнопка активна, только если выбрана строка и `model.getBooking(row) instanceof Editable`. Для `PastBooking` или без выбора она заблокирована.
* **Загрузка**: `JFileChooser` → `CsvLoader.load` → таблица обновляется. Диалог показывает, сколько записей загружено и сколько строк пропущено (с первыми причинами). Если файл не читается — диалог ошибки.
* **Сохранение**: `JFileChooser` → `CsvSaver.save`; ошибки записи — диалог.
* **Добавление**: открывает `BookingDialog` с `existing = null`; `id` = максимальный + 1.
* **Изменение**: открывает `BookingDialog` с выбранной бронью. Дополнительная защита: если объект не `Editable`, показывается ошибка.
* **Проверка конфликта комнаты** (`hasConflict`): при добавлении/изменении просматривается список, и если есть другая бронь той же комнаты с пересекающимся временем — диалог «Конфликт…», бронь не сохраняется. (Для регулярной брони проверяется только базовый интервал, повторения по дням не разворачиваются — это выходит за рамки лабораторной 1.)

### 5.2. `BookingTableModel`

Наследует `AbstractTableModel` — стандартный способ связать `JTable` со списком. Хранит `List<Booking>`, отдаёт таблице значения ячеек через `getValueAt` (7 колонок), предоставляет `add`, `replace`, `setAll`, `getAll` и уведомляет таблицу об изменениях (`fireTable...`). Именно за счёт этого модель (список броней) отделена от отображения (таблицы) — паттерн MVC.

### 5.3. `BookingDialog`

* Модальный `JDialog` с полями: тип, комната, сотрудник, начало, конец, комментарий, чекбоксы дней недели.
* Тип выбирается только из «Обычная» / «Регулярная» — read-only тип создать нельзя. При редактировании тип заблокирован.
* Поля, не относящиеся к выбранному типу, отключаются (комментарий для регулярной, дни для обычной).
* По «OK»: разбор дат (неверный формат → диалог ошибки) → создание нового объекта → `validate()` → при ошибках диалог со списком ошибок, окно остаётся открытым.
* Диалог **всегда возвращает новый объект**, а старый не меняет — если валидация не прошла, исходные данные не пострадали. В `MainFrame` при редактировании новый объект заменяет старый в той же строке.

## 6. Ход работы программы (кратко)

```
Запуск → Main → MainFrame (пустая таблица)
   │
   ├─ «Загрузить» → CsvLoader → список Booking → BookingTableModel → JTable
   │                                 └─ битые строки пропущены, число показано в диалоге
   ├─ «Добавить»  → BookingDialog → validate() → проверка конфликта → model.add
   ├─ «Изменить»  → (только для Editable) BookingDialog → validate() → конфликт → model.replace
   └─ «Сохранить» → CsvSaver → файл CSV
```

## 7. Запуск

1. Открыть папку проекта в IntelliJ IDEA как Gradle-проект (JDK 21).
2. Запустить `booking.Main` (зелёная стрелка) или выполнить `gradle run`.
3. «Загрузить из CSV» → выбрать `data/bookings.csv` (корректный файл) или `data/bookings_broken.csv` (в нём 7 строк с ошибками, загрузятся 2 корректные).

**Как показать на защите:**
1. Загрузить `bookings.csv` → выбрать строку «Прошедшая» → кнопка «Изменить» заблокирована.

5. «Сохранить в CSV» → загрузить сохранённый файл обратно.

## 8. Возможные вопросы преподавателя

**Почему `Booking` абстрактный?** «Бронь вообще» без вида не существует; абстрактный класс не даёт создать «пустую» бронь и заставляет наследников реализовать `csvType()` и др.

**Как гарантируется, что read-only нельзя изменить?** Три уровня: (1) `PastBooking` не реализует `Editable` — кнопка заблокирована; (2) в `onEdit` повторная проверка `instanceof`; (3) сеттеры `PastBooking` бросают исключение. Создать его через «Добавить» нельзя — в диалоге такого типа нет.

**Зачем `validate()` в интерфейсе?** Чтобы каждый редактируемый тип сам определял свои правила, а GUI и загрузчик вызывали единый метод, не зная конкретного класса.

**Почему список ошибок, а не `boolean`?** Пользователь видит все ошибки сразу, а не по одной; в загрузчике причина попадает в сообщение о пропущенной строке.

**Что происходит с битой строкой?** Она пропускается, остальные загружаются, число пропущенных и причины показываются в диалоге.

**Почему диалог создаёт новый объект, а не меняет старый?** Чтобы при ошибке валидации не оставить объект в наполовину изменённом состоянии.

**Почему `EnumSet` для дней недели?** Нет дубликатов, хранится порядок Пн–Вс, минимальный расход памяти.

**Что такое `record LoadResult`?** Неизменяемый класс-«пакет» данных (Java 16+): автоматически даёт конструктор и методы `bookings()` и `errors()`; удобно вернуть из метода два значения сразу.

**А структура данных «дерево интервалов» из варианта?** Относится к следующим работам (поиск пересечений за O(log n)). В лабораторной 1 бронирования лежат в `ArrayList`, конфликт ищется линейным проходом — для учебных объёмов достаточно.
